TICKET 011b — BUG: HistoricalAnalogWorkflow always returns invalid JSON [DONE]
- Symptom: every run logs "HistoricalAnalogWorkflow: LLM response was not
  valid JSON"; status still returns completed because the workflow handles
  the parse error gracefully, but structured_output is empty/degraded
- Root cause: model hits max_tokens=2048 and truncates mid-JSON before it
  can close the response object; the prompt + historical FRED data context
  is large enough (8,500+ input tokens) that the output regularly exceeds
  2048 tokens
- Fix: raise max_tokens for the historical_analog call (try 4096); if the
  response is still truncated, add a JSON repair step or split the output
  into smaller structured chunks
- Acceptance criteria:
    1. Full pipeline run produces valid JSON from HistoricalAnalogWorkflow
       on the short_war_thesis.toml example with no "invalid JSON" warning
    2. structured_output contains at least one analog period with all
       required fields (date_range, macro_conditions, outcome_summary)
    3. Tests confirm valid JSON output and analog field completeness

TICKET 013b — BUG: WebResearchWorkflow annotation step fails with 429 rate limit [DONE]
- Root cause: 5 web search queries each drive a multi-turn tool_use loop via
  WebSearchClient, consuming the full 30k input tokens/minute org limit before
  the annotation call is made; annotation call then fails with 429 immediately
- Fix: reduce _N_QUERIES_MAX from 5 to 3 in app/workflows/web_research.py;
  fewer search calls directly reduces token consumption at the source with no
  latency penalty; 3 queries is sufficient for focused thesis research
- The stop_reason='max_tokens' WARNING in WebSearchClient (no tool_use blocks)
  appears on every query and confirms each search call is already saturating
  its token budget — the solution is fewer calls, not sleeping after them
- Acceptance criteria:
    1. Full pipeline (MacroContext → … → Recommendation) completes without
       a 429 on the annotation step at Tier 1 token limits
    2. _N_QUERIES_MAX = 3 in web_research.py
    3. The existing max_tokens WARNING in WebSearchClient is documented as
       expected behaviour (model synthesises results after final tool_use round)
    4. Tests updated to reflect 3-query cap

TICKET 013c — BUG: WebResearchWorkflow queries 2 and 3 dropped by Tier 1 rate limit [DONE]
- Symptom: first web search query succeeds and consumes the full 30k token
  budget; queries 2 and 3 fail immediately with 429 and are silently dropped;
  annotation runs on results from 1 query only
- The 65s sleep in TICKET-013b protects the annotation call but does not
  protect between queries — the inter-query 429s still discard 2/3 of the
  searches
- Fix options (in preference order):
    1. Upgrade Anthropic account to Tier 2 (60k tokens/min) — cleanest,
       no code change; both remaining 429s would clear
    2. Add a per-query sleep (~65s) between searches so each query gets a
       fresh rate-limit window — works at Tier 1 but adds ~2 min to the run
    3. Reduce the search result payload size by setting allowed_domains on
       the web_search tool to primary sources only, reducing tokens per query
- Acceptance criteria:
    1. All 3 queries execute successfully on a full pipeline run
    2. WebResearch structured_output.sources reflects results from multiple
       queries, not just the first
    3. No 429 warnings logged during the search loop

TICKET 018 [DONE] — Intake Agent

  (1) a concise restatement of the thesis as the agent understood it
  (instrument, direction, time horizon, and macro mechanism), and
  (2) any clarifying questions the agent needs answered before the full
  research pipeline can run effectively (e.g. ambiguous instrument,

  are produced by FalsificationGenerationWorkflow in the research pipeline

  corrections to the restatement or answers to the agent's questions
- On response: user response stored, research workflow queued
- On timeout (configurable, default 24 hours): research workflow proceeds
  with original interpretation; thesis_confirmed set to False
- thesis_confirmed=False banner is non-dismissible until user explicitly
  acknowledges it via the UI
- Tests confirm intake generation, UI response handling, and timeout behavior

TICKET 018b [DONE] — Instrument Extraction from Intake Notes → thesis_instruments
- Gap: TICKET-018's intake agent restates the instrument in prose (as part
  of "## Thesis as I Understood It") but never persists it as structured
  data. No ticket in this list ever writes a ThesisInstrument row —
  `ThesisInstrument` is only ever defined (migration + model), never
  instantiated anywhere in app/. As a result every thesis currently has
  zero rows in thesis_instruments, which cascades into
  InstrumentAnalysisWorkflow and BacktestWorkflow both degrading to a
  PARTIAL result ("no instruments on thesis ...") — not because those
  workflows are broken, but because they correctly have nothing to
  analyze. This defeats a meaningful chunk of the research pipeline on
  every thesis run today.
- Fix:
    1. Extend the existing one-volley intake LLM call (IntakeService) to
       also extract a LIST of one or more instruments from thesis_title +
       notes, in addition to the existing prose restatement — no new LLM
       call needed, just a structured field alongside the existing
       response. Do not hardcode an assumption of exactly one instrument:
       the thesis_instruments schema already supports multiple rows per
       thesis via the role field (primary/hedge/secondary), specifically
       so multi-leg theses (spreads, pairs, hedges) don't require a schema
       change later (PRD Section 6.6) — this extraction step should honor
       that from day one even though v1 execution only acts on the
       primary leg.
    2. For each extracted instrument, the agent infers: ticker symbol,
       role (primary/hedge/secondary), and direction (long/short). Do NOT
       blindly copy the thesis-level `direction` field onto every
       instrument — a hedge leg may intentionally run the opposite
       direction from the primary (e.g. "long TLT, hedged with short
       IEF"). Exactly one instrument must be marked role=primary, and its
       direction should match the thesis-level `direction` captured at
       submission (TICKET-017); if the agent's extraction disagrees on
       the primary's direction, treat that as ambiguity (see point 4)
       rather than silently overriding either value.
    3. Write one ThesisInstrument row per extracted instrument, at the
       same point the intake_message is persisted
       (IntakeService.generate_intake_message) — before the user responds
       or the timeout fires, so they're available to the research
       pipeline either way.
    4. If any extracted instrument (ticker, role, or direction) is
       ambiguous or uncertain — including a primary-direction mismatch
       against the thesis-level field — the agent should raise it as one
       of intake's existing "clarifying questions" (per TICKET-018)
       rather than silently guessing. This already fits the intake
       message's existing structure; no new UI surface needed.
    5. v1 execution/position-sizing still only acts on the primary
       instrument (hedge/secondary legs are v2 execution scope per PRD
       Section 6.6) — this ticket is about research-side extraction and
       persistence being multi-instrument-ready, not about executing
       multi-leg trades.
    6. Known v1 limitation to flag, not solve here: if the user's intake
       response corrects an instrument in free text (e.g. "actually the
       hedge should be GLD, not IEF"), there is no mechanism to re-parse
       that correction into a structured update — intake is one-volley
       per PRD Section 4.2, and reconciling free-text corrections against
       thesis_instruments is out of scope for this ticket. Document this
       limitation in the intake response UI copy or leave a comment; do
       not silently attempt partial parsing.
- Acceptance criteria:
    1. Submitting a single-instrument thesis results in exactly one
       ThesisInstrument row (role=primary, direction matching the
       thesis-level field) once the intake message is generated
    2. Submitting a thesis whose notes describe multiple legs (e.g. a
       primary position plus an explicit hedge) results in multiple
       ThesisInstrument rows, each with its own role and direction —
       extraction is not hardcoded to a count of one
    3. InstrumentAnalysisWorkflow and BacktestWorkflow no longer degrade to
       PARTIAL for "no instruments" on a normally-submitted thesis
    4. A mismatch between the extracted primary instrument's direction and
       the thesis-level direction field surfaces as an intake clarifying
       question rather than a silent override
    5. Tests confirm single-instrument extraction, multi-instrument
       extraction, persistence of all rows, and the ambiguous-instrument
       question path

TICKET 032 — Position Sizer
- PositionSizer class computes target dollar allocation for a thesis
- Uses formula from PRD Section 6.2:
  position_size = (target_vol * nav) / realized_vol_60d
  position_size = min(position_size, 0.25 * nav)
- target_vol loaded from pod settings (default 5%)
- realized_vol_60d fetched from IBKR price history
- Returns target position size in dollars and number of shares
- Tests confirm correct formula application, cap enforcement, and correct
  behavior when volatility data is unavailable

TICKET 033 — Portfolio Manager
- PortfolioManager class maintains current target portfolio state
- compute_target_weights() returns target dollar allocation for all active
  theses using PositionSizer
- compute_rebalance_orders() diffs target weights against current IBKR
  positions and returns a list of required orders
- Orders below the rebalance threshold (1% NAV, from pod settings) are
  filtered out and logged as skipped
- Tests confirm correct diff computation, threshold filtering, and order
  list output

TICKET 034 — Order Executor
- OrderExecutor submits orders to IBKR Client Portal API
- Order direction (buy/sell) is always derived from thesis_instruments.direction — never hardcoded
- Submits limit order at mid-price; waits up to 5 minutes for fill
- On fill timeout: cancels limit order and resubmits as market order
- Logs all execution details to trades table: submitted_price, fill_price,
  fill_time, slippage, order_type
- Raises typed OrderExecutionError on failure; does not silently swallow
  errors
- Tests mock IBKR API and confirm limit-then-market fallback and logging

TICKET 035 — Close Trade Service
- CloseTrade service method exists in app/services/
- Accepts thesis_id and close_reason (human_manual, kill_condition, auto_close)
- Reads direction and role from thesis_instruments for each instrument in the thesis
- Submits a market sell order for long positions, buy-to-cover for short positions
- In v1 all positions are long — but close logic must read from thesis_instruments.direction, never assume long
- Updates thesis status to closed
- Writes to audit_log with changed_by, timestamp, and close_reason
- Sends confirmation email via AlertEmailService
- "Close Trade" button visible on brief page for active theses
- Button triggers a confirmation modal with Cancel and Confirm
- No action taken until Confirm clicked; modal dismisses on Cancel
- Kill authority workflow calls the same CloseTrade method — no separate implementation
- Tests confirm: full position close order submitted, status updated, audit entry written, email sent, and that human and agent paths call identical service method

TICKET 036 — Weekly Rebalance Job
- APScheduler job runs at Monday market open (9:35am ET)
- Calls PortfolioManager.compute_rebalance_orders()

- Logs rebalance run: orders submitted, orders skipped (below threshold),

- Manual rebalance trigger available via POST /portfolio/rebalance (requires

TICKET 037 — Paper vs. Real Mode Enforcement & Position Transition
- trading_mode field on pod_configs controls all IBKR routing
- IBKRClient reads trading_mode from pod_configs at request time — never cached
- UI displays current trading_mode prominently on every page
- Switching trading_mode requires explicit user action via UI confirmation
  modal; user must type "CONFIRM REAL TRADING" to proceed
- Paper → real transition executes in this exact order, each step with its
  own immediate audit_log entry:
    1. mode_switch_attempted logged
    2. Cash check against real IBKR account buying power
    3. cash_check_passed or cash_check_failed logged with amounts
    4. If failed: block switch entirely, alert user with shortfall, stop
    5. If passed: open real positions for all active theses at current sizing
    6. real_positions_opened logged per confirmed IBKR fill
    7. Close all paper positions
    8. paper_positions_closed logged per confirmed close
    9. trading_mode updated to real in pod_configs
- Real → paper transition executes in this exact order:
    1. mode_switch_attempted logged
    2. Close all real positions
    3. real_positions_closed logged per confirmed IBKR fill
    4. trading_mode updated to paper in pod_configs
    5. mode_switch_completed logged
    6. Paper account starts fresh — next rebalance populates paper positions
- Mid-process failures are logged and alerted immediately; no auto-rollback
- All audit entries written immediately when the step completes — never batched
- Tests confirm: cash check blocks switch on insufficient funds, each audit
  entry written at correct step, paper account fresh after real→paper switch,
  IBKRClient routing correct for each mode
